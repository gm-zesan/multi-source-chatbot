## 3. Concurrent Load-Test Throughput & Concurrency Audit

### A. Code & Timestamp Investigation
An audit of `scripts/run_production_load_test.php` (lines 163–229) revealed a critical architectural distinction regarding the reported "Concurrency = 5" load test:

```php
// Code snippet from scripts/run_production_load_test.php
for ($b = 0; $b < $totalBatches; $b++) {
    $batchResults = [];
    for ($c = 0; $c < $concurrency; $c++) {
        $t0 = microtime(true);
        $resp = $orchestrator->process(...);
        $elapsedMs = round((microtime(true) - $t0) * 1000, 2);
        ...
    }
}
```

### B. Auditor Findings on Concurrency & Throughput
1. **Concurrency was NOT genuinely simultaneous:** The test dispatched queries within a single synchronous PHP process using a nested `for` loop. Each request in a batch was executed strictly sequentially after the previous request finished.
2. **Throughput Calculation:** The reported throughput of `0.26 req/sec` was computed as:
   $$\text{Throughput} = \frac{20\text{ requests}}{75.53\text{ seconds}} \approx 0.265\text{ req/sec}$$
   Because requests ran serially, this value simply reflects the reciprocal of single-thread end-to-end latency ($\frac{1}{3.776\text{s}} \approx 0.265\text{ req/sec}$), rather than multi-threaded server concurrency saturation.
3. **Production Concurrency Implication:** In a live deployment using Nginx + PHP-FPM with multiple worker pools (e.g. 5–10 worker processes) or Laravel Octane:
   - 5 parallel incoming requests would be processed concurrently across separate worker processes.
   - At ~3.8s average latency per worker, a 5-worker pool would deliver an effective throughput of:
     $$\text{Effective Throughput}_{\text{5 workers}} \approx \frac{5}{3.8\text{s}} \approx 1.31\text{ req/sec}$$
4. **Audit Requirement:** True asynchronous multi-client saturation load testing must be conducted in the staging web tier using tools like k6, Locust, or `wrk` against Nginx before any unrestricted production rollout.

## 5. Kill Switch & Fail-Closed Boundaries Audit

### A. Multi-Path Coverage Matrix
The kill switch and tenant rollout boundaries were audited across all application entry points:

| Ingress Path | Mechanism | Kill Switch / Rollout Behavior | Fail-Safe Outcome |
| :--- | :--- | :--- | :--- |
| **Direct Synchronous Turn** | `UnifiedOrchestrator::process()` | Checks global mode & workspace status | Instant human handoff ($< 1\text{ ms}$) |
| **Queued Webhook Ingestion** | `ReceiveMessengerWebhookJob` $\rightarrow$ `RunFAQEngineListener` | Evaluates fresh DB state at turn start | Instant human handoff ($< 1\text{ ms}$) |
| **Queue Retries & In-Flight** | Worker retry attempt | Pulls fresh `$workspace->isAiRolloutEnabled()` | Halts immediately upon switch flip |
| **Missing Tenant Context** | `$workspaceId <= 0` | Fails closed in `limited_canary` | Routes to safe fallback handoff |
| **Unknown Workspace ID** | `$workspace === null` | Fails closed in `limited_canary` | Routes to safe fallback handoff |
| **General Rollout Mode ('all')**| `Workspace::setAiKillSwitch(true)` | Per-workspace kill switch overrides global mode | Merchant instantly isolated & halted |

### B. Implementation Hardening in `UnifiedOrchestrator.php`
Lines 59–95 were hardened to enforce strict fail-closed boundaries:
* If `$rolloutMode === 'limited_canary'` and `$workspaceId <= 0`: Rejects with `missing_tenant_context`.
* If `$rolloutMode === 'limited_canary'` and `$workspace === null`: Rejects with `unknown_workspace_unauthorized`.
* If `$rolloutMode === 'all'` and `$workspace->isAiKillSwitchActive()`: Rejects with `workspace_kill_switch_active`.
* Integer normalization in `Workspace.php`: Normalizes all comma-separated strings or integer arrays via `array_map(fn($v) => (int) $v, $canaryWorkspaces)`.

## 6. Telemetry Token Usage & Provider Billing Reconciliation

### A. Investigation of Reported Token Metrics
In `2026-11-24_production_load_test_metrics.json`, the load test reported:
- Total Tokens: 1,260 | Average Tokens/Query: 63 | Cost / 1k queries: \$0.0126 USD (~৳1.51 BDT)

**Audit Finding:**
Line 198 of `scripts/run_production_load_test.php` reveals why:
```php
$tokens = mb_strlen($workload['query'] . ($resp['reply'] ?? '')) / 3;
```
The test script probed `$resp['decision_metadata']['total_tokens']` instead of `$resp['raw_llm_response']['total_tokens']`. As a result, it fell back to a character heuristic (`strlen / 3`) that counted only visible customer-facing text, ignoring the system prompt and Typesense context chunks.

### B. Realistic Production Economic Model
When auditing full production dialogue turns against DeepSeek Chat API logs:
* **System Prompt & Router Instructions:** ~250 tokens
* **Retrieved Knowledge / Catalog Context:** ~100–150 tokens
* **Customer Query & Dialogue History:** ~40 tokens
* **LLM Completion (Generated Reply):** ~50–80 tokens
* **True Total Tokens per Turn:** **~420 to 520 tokens**

### Real DeepSeek Cost Calculation:
* Input: 440 tokens $\times \frac{\$0.14}{1,000,000} = \$0.0000616$
* Output: 60 tokens $\times \frac{\$0.28}{1,000,000} = \$0.0000168$
* Cost per query: $\approx \$0.0000784\text{ USD}$
* **True Estimated Cost per 1,000 Queries:** **~\$0.078 USD (~৳9.40 BDT)**

**Auditor Conclusion:** While the previous \$0.0126 figure was an artifact of string heuristics, the realistic cost of **~৳9.40 BDT per 1,000 customer queries** remains remarkably cost-effective and commercially viable for Bangladeshi e-commerce merchants.

## 7. Operational Limitations & Unresolved Risks

1. **Serialized Single-Process Benchmark:** Staging load metrics reflect serialized execution. True multi-threaded network concurrency must be monitored via APM (Datadog/Sentry) during Phase 1 canary traffic.
2. **Typesense Index Drift Risk:** Real-time catalog updates depend on transactional sync. If a merchant updates spreadsheet inventory while Typesense is restarting, a background reconciliation job (`documents:process-pending`) is required to prevent stale stock answers.
3. **External Provider Latency Jitter:** While DeepSeek P50 latency is ~3.8s, network transit spikes to China/US endpoints can occasionally push P99 to ~9.0s. OpenRouter circuit-breaker failover is active with a 10s timeout.
